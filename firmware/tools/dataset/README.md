# dbdata: the training-data contract and its tools

The DrillBalancer app records takes from the device (raw IMU, both
microphones, the level readings), labels them and uploads each one to the
private data repo `Tropaion/Drill_Balancer_Data`. This folder defines what
such a recording looks like and holds the Python package that reads,
checks, indexes and loads it for training:

- `dbdata/contract/`: `taxonomy.v1.json`, `meta.v1.schema.json`,
  `events.v1.schema.json` (JSON Schema 2020-12). These files are the single
  source of truth; the app, the validator and the data repo follow them.
- `dbdata/`: `io` (read/write a recording), `labels` (phases from events),
  `windows` (aligned IMU + audio windows), `dataset` (training loader),
  `validate`, `index`, `stats`, and `dbrec`: the decoder of the device's
  recording stream (`.dbrec`, the format of
  `firmware/components/recorder/include/rec_stream.h`), which also exports a
  take as a recording folder (IMU and audio cut to the time both cover);
  `autodetect`, the auto-labeller (the reference for the app's Kotlin port),
  and `synth`, synthetic recordings with ground truth from the simulator.
- `dbdata/contract/autodetect_params.json`: the auto-detector's parameters,
  versioned; `fixtures/autodetect/`: its golden fixtures for the app;
  `fixtures/finalize/`: streams and what `dbrec` exports from them, which the
  app's finalizer must reproduce; `fixtures/labels/`: label sets and what
  `labels` derives from them (phases, grammar issues, derived labels), which
  the app's port must reproduce.
- `repo_template/`: README, `.github/workflows/validate.yml` and git
  attributes for the data repo; `bootstrap_repo.py` copies them, plus the
  contract, into a clone of it.

`validate` takes recording folders or any folder above them; every folder
holding a `meta.json` is a recording, whatever its name (a misnamed one fails
`E_ID`). It exits with 0 when there are no errors (warnings allowed unless
`--strict`), 1 on errors and 2 on usage errors; a path without any recording
is one, but the other paths are still validated and `--report` is still
written. `index --report FILE` fails (exit 2) when FILE is missing.

## Data repo

```
README.md  taxonomy/taxonomy.v1.json  schema/*.schema.json
index.csv  stats.md                     generated by the Action only
.github/workflows/validate.yml
recordings/YYYY/YYYY-MM/<id>/           one recording
```

The recording id is `YYYYMMDDTHHMMSSZ_<install4>_<rand4>`: the UTC start,
4 base32 characters of a random per-install id and 4 random characters.
The phone only adds `recordings/...` (one commit per recording), so it never
conflicts with the index.

On a push to `recordings/**`, `taxonomy/**`, `schema/**` or the workflow
file the Action (concurrency group `index`):
1. checks out `meta.json`/`events.json` of every recording (sparse,
   blobless) plus the data files of the recordings to validate: those
   changed in the push, plus every recording `index --list-unchecked`
   names (not in `index.csv` yet, or any of its files changed since its
   last full check, which also covers pushes whose run was superseded in
   the queue);
2. checks out this folder from the public main repo at the tag
   `dataset-v1` (no secret needed);
3. checks the contract copies, validates those recordings, regenerates
   `index.csv` + `stats.md` and commits them. It works on the branch tip
   (not the pushed commit), so a queued run builds on the previous run's
   index commit. If another push lands before its own, it drops its index
   commit, resets to the new tip and regenerates there: generated files are
   never rebased or merged. Its only permission is `contents: write`.

An invalid recording stays in the repo with `valid=0`. A validator report
counts for a recording only if it is a full (not `--light`) check of the
very files in the tree (its `fingerprint`, which covers every file of the
folder), so a label edit or data change that raced the run is not marked
checked, and only its data-check codes are taken (the meta/events checks are
redone, so a copy of a recording under another folder name, which shares its
report entry, fails `E_ID` alone). The index keeps the data-check result of
earlier runs only while no file of the recording changed since that check
(column `checked`); otherwise the row gets `W_UNCHECKED` and an empty
`checked`, so `--list-unchecked` names it until the next full check (an edit
and its revert cannot bring an old result back). The fingerprint is
`git:` + the folder's tree id when git tracks the folder and its files match
`HEAD` (so the Action's sparse checkout, which lacks the data files, still
sees them change), else `sha:` + a sha256 over the name and content of every
file. The meta/events checks run on every recording each time, and one
malformed recording (`E_INTERNAL`) never stops the others.

Setting the repo up: create the empty private repo, clone it,
`bootstrap_repo.py <clone>`, review, commit, push. Tag the main repo
`dataset-v1` at a commit with this folder before the first upload.

## Format

### Files of one recording

| File | Content |
|---|---|
| `meta.json` | `drillbalancer.meta/1`: ids and versions, IMU profile (ODR, ranges, LPF, axis frame, accel calibration, mount axis, gyro bias, optional CTRL2/3/5 `registers`), audio (rates, channels, gain, clipping, muted spans), sync fit, gaps, level settings, session labels, derived labels, review status, quality flags, the take (`take_id`, `end_reason`, device stats), sha256 + size of every data file |
| `events.json` | `drillbalancer.events/1`: the labels (events, spans, holes) and `coverage_us`. Labels live only here, so editing them never rewrites data |
| `imu.csv.gz` | `seq,t_us,ax,ay,az,gx,gy,gz,flags`: raw int16 counts in the board frame (bit along -Z) before calibration. `seq` comes from the chip timestamp and counts across gaps; `t_us` is the device's esp_timer |
| `level.csv.gz` | `t_us,mode,flags,elevation_cdeg,yaw_cdeg,bubble_x_cdeg,bubble_y_cdeg,deviation_cdeg,zero_elevation_cdeg,zero_bubble_x_cdeg,zero_bubble_y_cdeg`: the 10 Hz level readings as the device reports them (mode 0 wall, 1 floor, 2 angle; flags as in the BLE angle packet). While `ZERO_SET` is on, elevation and bubble are relative to the zero in that row's `zero_*` columns (0 otherwise), so a zero set, moved or cleared during a take is followed row by row |
| `audio.flac` | 16 kHz, 16-bit; channel order in `meta.audio.channels` (`mic1`, `mic2`). `audio.wav` is allowed instead |
| `audio_sync.csv` | `frame,t_us` per I2S DMA block: frames received when the block's timestamp was taken |
| `device_events.csv` | optional: `t_us,code,arg,text`, the device's EVENT records (`MARK`, `TOUCH`, `BLE_LOST`/`BLE_BACK`, `IMU_LOST`/`IMU_BACK`, `VIB_START`/`VIB_STOP`, `PROFILE`); text ≤ 64 chars |

IMU flags: bit 0 filled (interpolated by the FIFO gap fill), bit 1 accel
clipped, bit 2 gyro clipped, bit 3 first sample after a gap. Bit 3 is set
exactly where `seq` jumps (a transport gap, a FIFO discontinuity, or an IMU
reset, after which `seq` goes on by the samples the device clock says are
missing); the
windows treat every seq jump as a gap even without the flag. Audio frames
filled with silence are listed in `gaps.audio_gap_frames`, whose total must
equal `gaps.audio_missing_frames`.

All times are device microseconds. Audio is placed on that clock by the
least-squares fit `t_us = a + b * frame` over `audio_sync.csv`
(`meta.sync` holds the same fit, plus `adc_delay_us` once it is measured).

### Labels

Point events (`t_us`): `motor_on`, `contact`, `breakthrough`, `retract`
(the bit leaves a blind hole), `motor_off`, `kickback`. `contact`,
`breakthrough` and `retract` carry `hole`. Span events (`t0_us`, `t1_us`,
may overlap): `stuck`, `wander`, `wobble` (problems), `handling` (moved with
the motor off), `ignore` with `reason` speech/bump/other (no loss there).
Each carries `source` (auto/user), `confidence`, after an edit `edited`
and the detector's `auto_t_us`, and `confirmed` once a person checked an
auto label.

Grammar (`labels.GRAMMAR`): a motor run is `motor_on`, holes, `motor_off`;
a hole is `contact`, then `breakthrough` or `retract`. Pecking the same
blind hole repeats `contact`/`retract` with the same hole number. The motor
may stop with the bit in the hole (stuck bit, aborted hole): the next
`motor_on` restarts in that hole, or a `retract` pulls the bit out with the
motor off. The labels may end in any state (a take stopped by `max_s`, the
battery or a lost link, see `meta.take.end_reason`): that is `W_OPEN_END`,
not an error.

Phases, one per sample, from one fixed state machine
(`labels.phase_segments`; the app's `Phases.kt` mirrors it). Window lengths
are `phase_params.windows_ms` in the taxonomy:

| Phase | From | To |
|---|---|---|
| `off` | start, end of spindown | next `motor_on` |
| `spinup` | `motor_on` | earlier of +300 ms and the next event |
| `free_run` | end of spinup, end of the breakthrough window, `retract` | next event |
| `drilling` | `contact`, end of spinup after a restart in the hole | `breakthrough` - 50 ms, `retract` or `motor_off` |
| `breakthrough` | `breakthrough` - 50 ms | +250 ms (or the next event) |
| `spindown` | `motor_off` (a `retract` with the motor off does not end it) | earlier of +600 ms and the next `motor_on` |
| `unknown` | outside `coverage_us`; from the event before an invalid one to the next `motor_off` | |

Every phase boundary has a guard of ±50 ms (`guard_ms`). The loader's
`boundary_policy`: `ignore` (weight 0 in the guard), `hard` (plain labels)
or `soft` (labels blend linearly across the guard). `unknown` and `ignore`
spans always weigh 0.

Recording-level labels are in `meta.session` (material, layers, mode, bit
type and diameter, drill type and motor, drill model, gear, speed setting,
outcome tags, notes) and can be overridden per hole in `events.holes[]` (`material: null`
inherits; a hole's `outcome_tags` replace the session's, and its derived
`off_angle` tag follows the hole's own off angle). `drill.type`
(taxonomy field `drill_type`): `drill` (a drill/driver without hammer),
`combi_drill` (with a percussion hammer), `rotary_hammer` (SDS),
`impact_driver`; `drill.motor` (field `motor`): `brushed`, `brushless`,
`universal_ac` (a corded AC universal motor: corded is said here, not by
the type). Both keys are required (`unknown` when not known), next to
`model`, `gear` and `speed_setting`; `other` texts go to
`other_text.drill_type` / `other_text.motor`. Ids are hierarchical (`wood/softwood`); `labels.map_to_level`
truncates them, `labels.coarse_phases` maps phases to coarse classes. Every
field accepts `unknown`, and `other` with `other_text`. Taxonomy entries are
only ever appended; retired ids get `deprecated` + `replaced_by`, and
`index.csv` and the window labels show the replacement (`Taxonomy.resolve`),
so filters match old and new data alike. `Taxonomy.problems()` self-checks
the file (`--contract` runs it).

Derived labels (computed, never typed; the validator recomputes them), from
the LEVEL rows with `IMU_OK` only:
- `orientation` from the median signed bit elevation during `drilling`
  (`elevation_cdeg` plus `zero_elevation_cdeg` on rows with `ZERO_SET`,
  `labels.absolute_elevation_deg`): wall if |e| < 30°, floor if e < -60°,
  ceiling if e > 60°, else angled;
- `off_angle_deg`: the median |deviation| during `drilling`; the tag
  `off_angle` is set when it is above the device tolerance (`level.tol_deg`).

### Validator checks

| Code | Check |
|---|---|
| `E_JSON`, `E_SCHEMA_META`, `E_SCHEMA_EVENTS` | JSON parses and matches the schemas (notes ≤ 200 chars, ...) |
| `E_TAXONOMY`, `E_OTHER_TEXT`, `W_DEPRECATED`, `E_TAXONOMY_VERSION`, `W_TAXONOMY_ADDED` | every id is in the taxonomy and not newer than the document's `taxonomy_version` |
| `W_MODE_TOOL` | `session.mode` contradicts `session.drill.type` (hammer with `drill` or `impact_driver`, screw with `rotary_hammer`: the taxonomy's `mode_tool_conflicts`); a warning only, `unknown` and `other` never warn |
| `E_ID` | folder, recording ids and `YYYY/YYYY-MM` agree; the id holds a real date |
| `E_FORBIDDEN_KEY`, `E_PII`, `E_PII_DATA` | no location, name, email, MAC (or similar) keys; no email or MAC addresses in text (the text of `device_events.csv` whenever the file is there, listed in `meta.files` or not) |
| `E_SHA`, `E_BYTES`, `E_MISSING_FILE`, `W_EXTRA_FILE`, `E_FILES_META` | data files match `meta.files` |
| `E_FILE_SIZE` | every file < 95 MB |
| `E_SEQ_ORDER`, `E_T_ORDER`, `E_IMU_FORMAT` | `seq` and `t_us` strictly increasing; counts are int16 |
| `E_ODR`, `W_ODR_META` | measured ODR within 2 % of nominal |
| `W_FILLED`, `W_MISSING`, `W_GAPS_META`, `W_GAP_FLAG` | filled < 15 %, missing < 1 %; flag bit 3 exactly at the seq jumps |
| `E_AUDIO_GAPS` | `audio_gap_frames` add up to `audio_missing_frames` |
| `E_DURATION` | audio and IMU durations within 1 % |
| `E_SYNC`, `E_SYNC_FORMAT`, `W_SYNC_META`, `E_AUDIO_FORMAT`, `E_AUDIO_META` | sync fit residual < 1 ms rms; audio rate, channels, 16-bit |
| `E_GRAMMAR`, `W_OPEN_END`, `E_HOLE`, `E_EVENT_ID`, `E_SPAN`, `W_HOLE_UNUSED`, `W_KICKBACK_OFF` | event grammar and holes |
| `E_EVENT_RANGE`, `E_COVERAGE`, `W_COVERAGE` | events and spans inside `coverage_us` |
| `E_LEVEL_FORMAT`, `E_LEVEL_ZERO` | level rows in time order with all columns; the `zero_*` columns are 0 on rows without `ZERO_SET` |
| `E_DERIVED` | derived labels match a recomputation |
| `E_DEVICE_EVENTS` | `device_events.csv` parses, is in time order, uses known codes |
| `W_REVIEW_STATUS`, `W_DETECTOR` | `review.status` `auto_only` means the detector's labels as it wrote them: no `user`, `edited` or `confirmed` label, and `events.detector` set; `meta.review.detector` names the same detector |
| `E_INTERNAL` | the validator itself failed on this recording (reported, never raised) |
| `W_UNCHECKED` | (index only) no full check of the recording's current files yet (`checked` is empty) |

### index.csv

`recording_id, path, start_utc, duration_s, session_id, imu_profile, odr_hz,
has_audio, material, mode, bit_type, bit_diameter_mm, drill_type, motor,
orientation, n_holes, phases, problems, outcome_tags, review_status,
min_confidence, taxonomy_version, valid, warnings, split, bytes, checked`.
List columns are
`;`-separated (`phases` as `phase=seconds`); `warnings` holds every issue
code, errors included; `checked` is the fingerprint of the recording's files
at the full check whose result the row holds, empty without one. `split` is `crc32(session_id) % 10`: 0-7 train, 8
val, 9 test, so all takes of one session (one workpiece) stay in one split.
An `index.csv` written before a column existed loads with that column empty
until the Action regenerates it.

`stats.md` (valid recordings, except the totals and the validator issues):
totals, splits, phase time, the minutes by material x mode and by drill
type x motor, then counts of review status, IMU profiles, orientation,
problems, outcome tags and validator issues.

## Loading data for training

```python
import sys; sys.path.insert(0, "firmware/tools/dataset")
from dbdata import Dataset, load_taxonomy

ds = Dataset(["~/data/Drill_Balancer_Data", "~/data/Drill_Balancer_Data_2027"],
             split="train",
             filters={"imu_profile": "RAW448", "mode": ["drill", "hammer"], "material": "wood"},
             win_s=1.0, hop_s=0.5, boundary_policy="ignore")
print(len(ds), "recordings")
a = ds.arrays()                    # valid windows of all recordings, npz-cached
x_imu = a["imu"]                   # (K, 448, 6) float32, m/s^2 and rad/s, calibrated
x_mic = a["audio"]                 # (K, 2, 16000) float32 in [-1, 1)
fill = a["fill_mask"]              # (K, 448) True where interpolated or padded
y = a["phase"]                     # (K,) index into load_taxonomy().phases
w = a["weight"]                    # (K,) loss weight (guards, unknown, ignore spans)
```

`Dataset` reads `index.csv` of each root (or builds it in memory for a
folder without one) and by default keeps valid, not rejected recordings
(with audio when the audio stream is requested). Filters take a value, a
list or a callable per index column; strings match hierarchically
(`"wood"` matches `wood/softwood`), list columns by membership
(`{"problems": "wobble"}`). The cache is `~/.cache/dbdata`
(`$DBDATA_CACHE`, `cache_dir=False` turns it off); its key hashes
`meta.json` and `events.json` as a whole (so a later `adc_delay_us` or a
calibration edit is picked up), the taxonomy version and the window options.
The array keys and per-window shapes follow from the options (`soft` under
`boundary_policy="soft"`, `audio` with the audio stream), so a recording
shorter than one window adds none and still stacks with the rest; a window
without a single IMU sample (inside a long gap) is `unknown` with weight 0
(and a one-hot `unknown` soft label).

Lower level:

```python
from dbdata import read_recording, iter_windows, phase_track

rec = read_recording(path, calibrate=True, mount=True)   # rec.imu, rec.audio, rec.sync, rec.events
for w in iter_windows(rec, 1.0, 0.5, streams=("imu", "audio"), label="majority"):
    if w["valid"]:
        ...
track = phase_track(rec.t_us, rec.events, boundary_policy="soft")   # per-sample codes, weight, soft
```

Each window's `labels` (`recording_labels`) are the recording-level labels
of the hole it lies in: `material`, `mode`, `bit_type`, `bit_diameter_mm`,
`drill_type`, `motor`, `orientation`, `off_angle_deg`, `imu_profile`,
`outcome_tags`, `hole` (deprecated ids resolved like index.csv's).

`write_recording(dest, meta, events, imu, level=..., audio=..., audio_sync=...,
derive=True)` writes a complete folder and fills `meta.files` (and
`meta.derived`); the tests and the synthetic-data generator use it.

## Auto-detector

`dbdata.autodetect` labels a recording from its signals: it writes a
complete `events.json` (`source: auto`, a `confidence` per label,
`detector: {version, params_sha256}`) and the derived labels. The app runs
the same algorithm in Kotlin right after a take (milestone 6), and a
person reviews the labels there; `--write` relabels recordings on the PC
(`review.status` becomes `auto_only`; reviewed or edited labels need
`--force`), and validate checks that `auto_only` labels are untouched
(`W_REVIEW_STATUS`, `W_DETECTOR`). The algorithm, step by step, is the
module docstring of `dbdata/autodetect.py`; every number it uses is in
`dbdata/contract/autodetect_params.json`, whose sha256 (CRLF normalised to
LF) goes into each `events.json`. Change a value, bump its `version` for an
algorithm change, and regenerate the fixtures' expected output.

In short, on 10 ms frames:
- features: IMU energy above 20 Hz, the thrust along the bit (2-20 Hz),
  the roll rate about the bit, a hammer-blow periodicity; MIC1's level,
  the motor's fundamental f0 (harmonic product spectrum over a 32 ms
  window, zero-padded to 2048), the cutting band (1-6 kHz), spectral flux;
  z-scores against the quietest 0.5 s; where the transport lost data
  (`gaps.audio_gap_frames`, frames without IMU samples) there are no
  features, and the motor hysteresis waits the gap out;
- motor runs by hysteresis on the louder stream (a run the IMU never
  confirms is sound alone, e.g. speech), the motor_off walked back to where
  the energy and then f0 start to fall (also when the take ends in the
  spin-down, before the motor is quiet: the louder stream's last 50 ms
  10 dB below the run, and the motor slowing: its last voiced f0 falling,
  or without one the stream below the on threshold);
- contact when a weighted score of f0 sag, cutting noise, IMU energy and
  thrust (or the hammer blows) holds for 200 ms; the load end when f0 and
  the cutting noise recover; a breakthrough when an impulse comes with it
  (axial, radial gyro or a sound burst), else a retract;
- a stuck span (voiced f0 far below the free run or, with the harmonics
  gone, the IMU below its free-run level while the motor runs; also while
  hammering, and a stalling motor is no load end), restarts in the hole
  (or a retract when the bit was pulled out with the motor off), kickbacks
  (roll about the bit), and the suggestions wobble, wander and speech
  (confidence at most 0.5).

What it achieves on synthetic takes (`synth`'s `eval` set: 21 takes, drill
and hammer, 147/180/233 Hz motors with 10-30 % sag, blind holes, stuck bits
(also while hammering, and a quiet slow motor restarting in the hole),
kickbacks, quiet and noisy rooms, floor and ceiling, RAW897), with the
contract's tolerances (motor ±30 ms, contact ±100 ms, breakthrough ±50 ms;
retract and kickback ±100 ms, spans at IoU ≥ 0.5):

| | event F1 | mean timing error |
|---|---|---|
| motor (on + off) | 0.959 (on 0.919, off 1.0) | on 10 ms, off 4 ms |
| contact | 1.0 | 4 ms |
| breakthrough | 1.0 | 0.2 ms |
| retract, kickback, stuck | 1.0 | 17 ms, 2 ms |
| phases (10 ms frames) | accuracy 0.993 per take on average, 0.974 the lowest | |

Three more seed sets of the same scenarios gave motor_on 0.892, 0.892 and
0.865, phases 0.971-0.979 at the lowest, and the rest unchanged; so did 60
random takes around them (motor_on 0.81) and 36 takes of stalls (drill and
hammer, a quiet slow motor) and blind holes with a small sag.
`tests/test_autodetect.py` holds the eval set one miss below the worst of
the four seed sets, and a holdout in a room twice as loud. The eval takes
cut every 0.1 s (2040 cuts) find every motor_off that lies 0.4 s or more
before the cut (1054; detector 1.1.0 missed 112 of them, up to 0.82 s
into the spin-down) and no motor_off in the 1512 cuts where the motor
still runs (spin-up, free run, drilling, stalls).

Known limits:
- motor_on comes late when the room is loud or the drill quiet: the first
  part of the spin-up drowns (the motor's vibration stays below the 20 Hz
  high-pass for its first ~10 % of speed, and its sound below the room).
  On the eval scenarios with the room's sound scaled (everything else
  unchanged):

  | room | motor_on F1 (±30 ms) | median / 90th percentile lateness |
  |---|---|---|
  | ×1 | 0.92 | 9 ms / 26 ms |
  | ×1.5 | 0.81 | 25 ms / 72 ms |
  | ×2 | 0.62 | 25 ms / 82 ms |
  | ×3 | 0.19 | 54 ms / 85 ms |

  motor_off, contact, breakthrough, retract and stuck stay at 1.0 up to ×3.
  The simulator's spin-up starts gently (a smoothstep from standstill);
  whether a real motor is found earlier is for milestone 8.
- Without audio only the motor runs are found, about 60 ms (on) and 200 ms
  (off) late (contact needs the microphone).
- Labels inside a transport gap cannot be found; a gap within about
  0.5 s of a contact or a load end can move or hide it.
- The noise floor and the free-run level come from the take itself: a
  take with no 0.5 s of motor off (the motor runs from its first to its
  last frame) gets no labels at all, and a take that starts with the
  motor running needs about 0.15 s of free run before the contact (one
  sooner is missed, and the rest of that hole with it).
- The device's level is no reference while hammer blows shake it, so
  wander is not looked for in hammered holes.
- Every number comes from the simulator: thresholds, the noise floor
  rules, the stall levels and the hammer cue must be checked on real takes
  (milestone 8).

## Synthetic recordings and the golden fixtures

`dbdata.synth` writes complete recordings with ground truth. There is one
drilling model, the simulator's (`firmware/tools/sim`: `DrillScenario` for
the motion, the motor and the impacts, `core/sim_audio.c` for the
microphones). synth imports it by path and drives a whole simulated device
the way the app does: recorder session over the simulated link, a take, a
scenario played during it, the stream pulled in process. The take then
goes through `dbrec`'s decoder and export like a real one (the FIFO-loss
model's filled samples, the profile switch, the DMA block timestamps, the
device's own LEVEL rows), and the scenario's truth becomes `events.json`
(`source: user`, confidence 1, `review.status: reviewed`, `app.tool:
dbdata.synth`). It needs the simulator's C core (`libdbsim.so`, built on
demand with cmake and the ESP-IDF tree, see `tools/sim/README.md`) and
nothing from the simulator's Python requirements. Its tests are skipped
without it. `Spec` describes a take (scenario arguments, IMU profile,
microphones, noise and the room's sound, pose, labels; a mount
calibration first, a take that starts after the scenario or stops before
its end, a stalled stream client with a small ring for a transport gap,
and the injected wobble / wander / speech the simulator has no model
for); `SETS` holds the evaluation and fixture sets.

`fixtures/autodetect/<name>/` are eight short takes for the app's
`AutoDetectVectorsTest`: the recording's files (input), `spec.json`,
`events.json` (the truth), and the detector's expected output,
`expected.json` and `features.csv.gz` (every frame's features). The
fixtures, what each covers, the format and the tolerances are in
`fixtures/autodetect/README.md`.
`python -m dbdata.synth fixtures fixtures/autodetect` regenerates them
(the simulator); after a change to the detector, `python -m
dbdata.autodetect --update-fixtures` rewrites only the expected output, and
`--check-fixtures` (also a unit test) replays them.

`fixtures/finalize/` holds three takes as the app's journal has them (the
firmware's golden stream, a rich synthetic take, and that take cut off
mid-record) and what `dbrec.export_take` writes from each: the app's
`FinalizerCrossCheckTest` compares its own output with them. After a change
to the export, `.venv/bin/python fixtures/finalize/make_fixtures.py`
rewrites them; a unit test (`--check`) fails while they are stale.
`fixtures/finalize/README.md` says what is compared.

`fixtures/labels/phases.json` holds 279 label sets (the event orders of
`tests/test_labels.py`, the autodetect fixtures' truth and detector labels,
and seeded random sequences, valid and not, each with a synthetic LEVEL
table) and what `labels.phase_segments`, `labels.grammar_state` and
`labels.compute_derived` give for them. The app's `PhasesCrossCheckTest`
must reproduce them exactly. After a change to `labels.py`,
`.venv/bin/python fixtures/labels/make_fixtures.py` rewrites the file; a
unit test fails while it is stale.

## Changing the contract

- New labels: append entries, bump `version`, never rename or remove ids.
- A schema change that old recordings still pass stays `/1`; anything else
  is a new schema version and a new pinned tag (`dataset-v2`) in the
  workflow.
- Order: change the contract here and move the tag `dataset-v1` (or create
  the next one); then update the data repo's copies with
  `bootstrap_repo.py --force` and push; then ship the app that writes the
  new ids. The Action fails while the copies differ from the pinned dbdata,
  and a recording with a newer `taxonomy_version` than the validator knows
  fails with `E_TAXONOMY_VERSION`.
- A change in place (no `version` bump: the drill type and motor fields,
  made before the first recording) is not caught by `E_TAXONOMY_VERSION`:
  until the tag moves, the pinned validator rejects every recording the new
  app writes (`E_SCHEMA_META`, indexed `valid=0`). `bootstrap_repo.py
  --check-pin` compares the dbdata at the workflow's `DBDATA_REF` with this
  checkout (uncommitted changes included) and exits 1 while they differ;
  copying with `bootstrap_repo.py` warns too. The steps: commit; `git tag
  -f dataset-v1 && git push --force origin dataset-v1`; `--check-pin`
  passes; `bootstrap_repo.py <clone> --force`, commit and push the data
  repo; only then ship the app. A recording that was uploaded before is
  validated again by a manual run with `all` (workflow_dispatch).
